# Peirce self-development

## Purpose

Support deliberate improvement of Peirce while keeping source publication and
runtime learning isolated.

Use this skill only when the trusted current context is an explicitly configured
Peirce source project and the requested work is genuinely about Peirce's own
development. This public snapshot is not connected to live Peirce.

## Authorities

Treat the accepted source workspace as the authority for proposed product,
behavior, and policy changes. Repository history and current source are evidence
about what can be reviewed and published.

Treat the bounded live-learning snapshot as evidence about current runtime memory
and learned skills. It may inform source work, but it is not a source checkout,
publication target, or project association.

Require fresh, exact evidence for claims about either side. A semantic summary,
search result, or recollection does not establish exact live bytes.

## Comparing learning and source

Make overlap visible when the same relative skill or concept exists in source and
live learning. Preserve both observations and describe meaningful differences.

Judge conflicts explicitly. Do not silently prefer, merge, overwrite, synchronize,
or normalize one side from the other.

Keep project-specific learning in the repository. Shared profile memory and skills
remain runtime learning unless a reviewed change intentionally expresses a durable
source improvement.

## Reviewed outcome

Develop accepted changes on a task branch in the isolated source workspace. Keep
the proposal bounded to the trusted request and the evidence that supports it.

Publication means presenting a pull request for human review. Before pushing a
branch or creating a pull request, review all private, personal, and live-
learning material and remove anything not safe for a public repository. A public
repository is never a raw memory-sync target; review after merge is too late.
Do not infer approval or publish automatically merely because an improvement
appears useful.

Completion evidence should identify the accepted source state, relevant fresh
learning evidence, the visible conflict judgment, validations performed, and the
reviewable branch or pull-request outcome.

A human merge decision is separate from preparation and publication. A later
deployment is separate from merge and should not be claimed as part of this work.

## Boundaries

Do not turn runtime profile content into an alternate Git scope or publication
state. Never copy live memory wholesale into source, and never treat public
source as a raw runtime-memory sync destination.

Record why selected learning evidence is relevant to the proposed improvement and
what contrary evidence was considered; relevance alone does not settle a conflict.

If exact evidence is unavailable or changed during observation, preserve the
uncertainty and withhold completion until fresh exact evidence is established.
